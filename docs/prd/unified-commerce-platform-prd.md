## 1. الملخص التنفيذي

### 1.1 الرؤية في جملة واحدة

> **نظام تشغيل تجاري واحد (Commerce OS) يجمع بين قوة Shopify المعمارية، وعمق Vondera التشغيلي في السوق المصري/الخليجي، وسرعة EasyOrders في تحويل إعلانات السوشيال إلى أوردرات دفع عند الاستلام — بأسرع واجهة متاجر في المنطقة، وطبقة تكاملات مفتوحة تربط كل شيء بكل شيء.**

### 1.2 لماذا الآن؟

السوق العربي (مصر، السعودية، الإمارات، المغرب العربي) عالق بين ثلاثة خيارات كلها ناقصة:

1. **Shopify:** الأقوى معمارياً وبيئة تطبيقات ضخمة (Hydrogen/Oxygen، Storefront API، Functions، Checkout Extensibility)، لكن:
   - غير مصمّم أصلاً للـ COD (الدفع عند الاستلام) الذي يمثل الحصة الأكبر من الأوردرات في مصر والمغرب.
   - لا يوجد ربط أصلي مع شركات الشحن المحلية (بوسطة، مايلرز، شيب بلو، J&T، أرامكس مصر) بدون تطبيقات طرف ثالث.
   - التكلفة بالدولار + عمولة بوابة الدفع الخارجية (حتى 2% إضافية عند عدم استخدام Shopify Payments) تقتل هامش التاجر الصغير.
   - لا تسوية تلقائية لأموال الـ COD ولا مركز تأكيد أوردرات.
2. **Vondera:** ممتاز تشغيلياً للسوق المصري (مخزون، أوردرات، تقارير، تطبيق موبايل للتاجر، ربط بوسطة/QP Express وPaymob/Kashier/PayTabs/MyFatoorah، اشتراك يبدأ من ~300 ج.م/شهر)، لكن:
   - محرك الواجهة (Storefront) محدود التخصيص مقارنة بـ Liquid/Hydrogen.
   - لا يوجد متجر تطبيقات مفتوح ولا نظام إضافات لطرف ثالث بحجم يذكر.
   - قدرات التسويق/القمع البيعي (Funnels) أضعف من المنافس المتخصص.
3. **EasyOrders:** الأسرع في تحويل حملة فيسبوك/تيك توك إلى أوردر COD (لاندنج بيدج، فورم سريع، ربط بيكسل + Conversion API، تأكيد واتساب، دروب شيبنج، تسعير يبدأ مجاني بعمولة صغيرة لكل أوردر أو ~$50 شهرياً)، لكن:
   - ليس متجراً كاملاً بمعنى الكتالوج/الفاريانتس/المخزون متعدد المستودعات/B2B.
   - محدود في التوسع لتاجر يكبر لـ 10 آلاف أوردر شهرياً.
   - لا توجد منظومة إضافات ولا API ناضج للمطوّرين.

**الفجوة:** لا توجد منصة واحدة تعطي التاجر العربي: عمق Shopify + محلية Vondera + سرعة تحويل EasyOrders، في منتج واحد، بسعر محلي، وبأداء واجهة يقيس بالمللي ثانية.

### 1.3 المقترح القيمي (Value Proposition)

| للفئة | الوعد |
|---|---|
| التاجر المبتدئ (Media Buyer / Dropshipper) | «من إعلان لأوردر مؤكّد وبوليصة شحن مطبوعة في أقل من 90 ثانية — ومجاناً حتى أول 100 أوردر» |
| التاجر النامي (Brand) | «متجر بسرعة LCP < 1.2 ثانية على 3G، مخزون متعدد المستودعات، وتسوية COD تلقائية» |
| المؤسسة / Enterprise | «Headless API-first، Functions قابلة للبرمجة، SLA 99.95%، ونسخة self-hosted بترخيص مؤسسي» |
| الوكالات والمطوّرين | «متجر تطبيقات + Theme Marketplace + White-label مع مشاركة إيرادات 80/20» |

### 1.4 المتغيّرات الحاسمة (Non-negotiables)

1. **السرعة** — ميزانية أداء صارمة مفروضة في الـ CI؛ أي Theme أو App يكسر الميزانية لا يُنشر (القسم 8).
2. **الربط** — طبقة تكاملات موحّدة (Integration Fabric) بمنطق إعادة محاولة، Idempotency، وWebhooks موثوقة (القسم 9).
3. **COD كمواطن من الدرجة الأولى** — لا كإضافة، بل كمسار كامل: تأكيد → بوليصة → تحصيل → تسوية → مرتجع.

## 2. المشكلة والفرصة

### 2.1 مشاكل التاجر (موثّقة من سلوك السوق)

| # | المشكلة | الأثر الحالي | كيف نحلّها |
|---|---|---|---|
| P1 | نسبة رفض/إلغاء أوردرات COD تصل 25–40% | خسارة تكلفة شحن ذهاب وعودة | مركز تأكيد أوردرات + كشف الأوردر الوهمي + تأكيد واتساب تلقائي (§6.5) |
| P2 | تشتّت الأنظمة: متجر + إكسل + واتساب + لوحة شركة شحن | أخطاء يدوية، تأخير، لا رؤية موحّدة | نواة واحدة + Integration Fabric (§7، §9) |
| P3 | بطء المتجر على شبكات المحمول الضعيفة | كل +1 ثانية = هبوط تحويل ملموس | Edge rendering + ميزانية أداء (§8) |
| P4 | صعوبة تتبع الإسناد بعد iOS 14.5 | ميزانية إعلانات محروقة | Server-side CAPI + Deduplication + First-party tracking (§6.9) |
| P5 | تسوية أموال الـ COD يدوية وغير مطابقة | فجوات نقدية ونزاعات مع شركة الشحن | محرك تسوية COD تلقائي (§6.7) |
| P6 | التسعير بالدولار وعمولات مضاعفة | هامش مقتول للتاجر الصغير | تسعير محلي هجين (§10) |
| P7 | لا مسار نمو من «متجر لاندنج» إلى «براند» | التاجر يهاجر لمنصة أخرى ويخسر بياناته | نفس المنتج، ترقية باقات بلا هجرة (§10.4) |

### 2.2 حجم الفرصة (TAM/SAM/SOM — إطار للتقدير)

> **ملاحظة:** الأرقام أدناه إطار حسابي يجب تثبيته ببيانات سوق محدّثة قبل عرض المستثمرين؛ لم تُشتق من مصدر مُحقّق في هذه الوثيقة.

- **TAM:** إجمالي تجار التجزئة الرقميين في MENA.
- **SAM:** التجار الذين يستخدمون منصة SaaS مدفوعة أو مجانية بعمولة في مصر/السعودية/الإمارات/المغرب.
- **SOM (٣ سنوات):** استحواذ على شريحة «التاجر النامي» (50–5000 أوردر/شهر) عبر ميزة السرعة + التسوية + التكاملات المحلية.
- **محرّك النمو الأساسي:** PLG (باقة مجانية بعمولة لكل أوردر) + قناة الوكالات/الشركاء + متجر التطبيقات.

### 2.3 خارج النطاق (Out of Scope للإصدار 1)

- سوق متعدد البائعين عام (Marketplace مثل أمازون) — نوفّر Multi-vendor كوحدة اختيارية في المرحلة 4 فقط.
- تصنيع/MRP كامل، محاسبة كاملة (نكتفي بالتصدير والربط مع أنظمة محاسبية).
- خدمات لوجستية مملوكة (لا نمتلك أسطول شحن — نحن طبقة تجميع Aggregation).

### 3.2 ما نستنسخه بوعي (Deliberate Borrowing)

**من Shopify:**
- بنية **API-first** مع GraphQL Storefront API + Admin API وWebhooks موثوقة.
- مفهوم **Functions**: منطق تجاري قابل للاستبدال من طرف ثالث (خصومات، شحن، دفع، تحقق من السلة) يُنفّذ في بيئة معزولة (WASM/Isolate) عند حافة الشبكة.
- **Checkout Extensibility**: تخصيص الشيك أوت بامتدادات UI بدل تعديل الكود الأساسي — يحفظ الأمان والأداء والقابلية للترقية.
- **Edge hosting للواجهة** (نظير Oxygen) مع نشر عالمي وCache على مستوى الحافة.
- **Markets**: بيع متعدد الدول/العملات/اللغات من نفس المتجر.
- منظومة **App Store + Theme Store** بمشاركة إيرادات كمحرّك نمو.

**من Vondera:**
- **العمق التشغيلي المحلي**: إدارة مخزون لحظية، تنبيهات نفاد، معالجة أوردرات، تتبع مصروفات، أدوار فريق، تقارير مبيعات.
- **تطبيق موبايل للتاجر** كواجهة أساسية وليست ثانوية (التاجر المصري يدير من الموبايل).
- **ربط أصلي** مع بوسطة/QP Express للشحن وPaymob/Kashier/PayTabs/MyFatoorah للدفع.
- **تسعير بالجنيه** مع باقة مجانية للتجربة.

**من EasyOrders:**
- **مسار الأوردر فائق القِصَر**: لاندنج بيدج → فورم COD بحقول قليلة → أوردر.
- **مجاني بلا حد أوردرات** مع عمولة زهيدة لكل أوردر كبديل للاشتراك.
- **تأكيد واتساب** ورسائل ما بعد الشراء.
- **بيكسل + Conversion API** مدمج افتراضياً.
- **دروب شيبنج وأفلييت** كوحدات أصلية.
- **أكاديمية تعليمية** كأداة تفعيل واحتفاظ (Activation/Retention).

**من Salla/Zid:**
- كثافة الشركاء اللوجستيين (هدف: 40+ ناقل عند الإطلاق، 200+ خلال 24 شهراً).
- التوطين العميق (فاتورة ضريبية، ZATCA، اللغة، الهوية البصرية العربية RTL).

### 3.3 التموضع (Positioning Statement)

> لـ **التاجر العربي الذي يبيع عبر السوشيال ويريد أن يصبح براند**،
> الذي **يعاني من تشتت الأدوات وبطء المتجر ورفض أوردرات الـ COD**،
> **ركيزة** هي **نظام تشغيل تجاري موحّد**
> الذي **يشغّل المتجر والتأكيد والشحن والتحصيل والتسويق من نواة واحدة فائقة السرعة**،
> على عكس **Shopify (غالٍ وغير محلي) وEasyOrders (محدود التوسع) وVondera (محدود التخصيص)**،
> منتجنا **يقدّم العمق والمحلية والسرعة معاً، بترخيص مرن يبدأ من صفر**.

## 4. المستخدمون والشخصيات (Personas)

### P1 — «محمود» — الميديا باير / الدروب شيبر
- 24 سنة، يدير 3 متاجر لاندنج، يصرف 500–3000 ج.م/يوم إعلانات.
- **الوظيفة المطلوب إنجازها (JTBD):** «حوّل الترافيك لأوردر مؤكّد بأقل احتكاك وأقل تكلفة ثابتة.»
- **مقاييس نجاحه:** CPA، نسبة تأكيد الأوردرات، نسبة التسليم (Delivery Rate).
- **يحتاج:** لاندنج سريع، فورم بحقلين، CAPI دقيق، تأكيد واتساب، بوليصة شحن بضغطة، بلا اشتراك شهري ثابت.

### P2 — «سارة» — صاحبة براند ناشئ
- تبيع منتجات عناية، 300–1500 أوردر/شهر، مخزون حقيقي، فريق 4 أفراد.
- **JTBD:** «شغّل عمليات البراند بلا فوضى، واعرف أرباحي الحقيقية.»
- **تحتاج:** كتالوج بفاريانتس، مخزون متعدد المواقع، صلاحيات فريق، تقارير ربحية بعد الشحن والمرتجع، ولاء عملاء.

### P3 — «كريم» — مدير تجارة إلكترونية في شركة متوسطة/كبيرة
- 5000+ أوردر/شهر، ERP قائم، فروع فعلية.
- **JTBD:** «اربط المتجر بالـ ERP والـ POS بدون ما أكسر حاجة، وبـ SLA.»
- **يحتاج:** Headless API، Webhooks موثوقة، بيئة Staging، سجل تدقيق، SSO، عقود SLA.

### P4 — «هبة» — وكالة/مطوّر
- تبني متاجر لعملاء وتبيع صيانة.
- **JTBD:** «ابنِ بسرعة، امتلك العلاقة مع العميل، واكسب دخلاً متكرراً.»
- **تحتاج:** لوحة شركاء متعددة العملاء، White-label، CLI + Theme SDK، بيئة تطوير، مشاركة إيرادات.

### P5 — «أحمد» — موظف عمليات (Ops/Confirmation Agent)
- يعمل داخل مركز تأكيد الأوردرات.
- **يحتاج:** قائمة مهام (Queue)، شاشة اتصال/واتساب مدمجة، أسباب إلغاء منظّمة، مؤشرات إنتاجية.

### P6 — «المشتري النهائي»
- على شبكة محمول متذبذبة، يشتري من إعلان، يفضّل الدفع عند الاستلام، ويثق بواتساب.
- **يحتاج:** صفحة تفتح فوراً، شراء بلا تسجيل، تتبع شحنة واضح، تواصل سهل.

## 5. مبادئ المنتج ومقاييس النجاح

### 5.1 المبادئ (تُستخدم لحسم الخلافات)

1. **السرعة ميزة، لا تحسين لاحق.** أي ميزة تُقاس بأثرها على LCP/INP قبل الدمج.
2. **الافتراضي يجب أن يكون صحيحاً.** التاجر لا يجب أن يضبط 12 إعداداً ليبيع.
3. **كل شيء له API.** ما لا يمكن ربطه لا يُعتبر مكتملاً.
4. **البيانات ملك التاجر.** تصدير كامل بلا احتجاز (No lock-in) — نكسب بالقيمة لا بالحبس.
5. **COD مواطن من الدرجة الأولى.**
6. **التوسّع بلا هجرة.** نفس المنصة من أول أوردر إلى المليون.
7. **الامتداد قبل التخصيص.** نضيف نقاط امتداد بدل تعديل النواة.

### 5.2 النجم الشمالي (North Star Metric)

> **إجمالي البضاعة المُسلَّمة والمُحصَّلة عبر المنصة (Delivered & Collected GMV) لكل تاجر نشط شهرياً.**

اخترنا «المُسلَّمة والمحصَّلة» لا «المباعة» لأن قيمة المنصة الحقيقية في سوق COD تظهر بعد التسليم والتحصيل، لا عند إتمام الطلب.

### 5.4 معايير الاعتماد (Launch Gates)

الإصدار لا يُطلق ما لم تتحقق **كل** الشروط:
- `G1` ميزانية الأداء مُحقّقة على متجر مرجعي (§8.2).
- `G2` مسار COD كامل يعمل من الطلب إلى التسوية مع ناقلين اثنين على الأقل.
- `G3` معدل نجاح Webhooks ≥ 99.5% خلال 7 أيام.
- `G4` اختبار اختراق خارجي بلا ثغرات Critical/High مفتوحة.
- `G5` استعادة من نسخة احتياطية مُختبرة فعلياً (RTO ≤ 1 ساعة، RPO ≤ 5 دقائق).

### 7.2 قرارات معمارية (ADR مختصرة)

| # | القرار | البديل المرفوض | السبب |
|---|---|---|---|
| ADR-1 | **Modular Monolith** للنواة + خدمات منفصلة للمجالات عالية التقلّب (الشحن، الدفع، التحليلات) | Microservices كاملة من اليوم الأول | سرعة التسليم وبساطة التشغيل؛ نقسّم عند حدود مثبتة بالحمل |
| ADR-2 | **PostgreSQL** كمصدر حقيقة مع تجزئة أفقية بالـ tenant لاحقاً | NoSQL أولاً | المعاملات المالية والمخزون تحتاج ACID |
| ADR-3 | **Multi-tenant مشترك** مع عزل بالـ Row-Level Security + مفاتيح تشفير لكل tenant؛ **Silo (DB منفصل)** للمؤسسات | Tenant لكل DB للجميع | التكلفة والصيانة؛ نقدّم العزل الكامل كميزة مدفوعة |
| ADR-4 | **Event-driven** بنمط Transactional Outbox | استدعاءات متزامنة متسلسلة | التكاملات الخارجية غير موثوقة؛ نحتاج فصل ومحاولات إعادة |
| ADR-5 | **Edge rendering** للواجهة مع ISR ووسم Cache (Cache Tags) | SSR مركزي | زمن الاستجابة في مصر/الخليج هو المتغير الحاسم |
| ADR-6 | **GraphQL Persisted Queries** للواجهة و REST للعمليات الإدارية البسيطة | GraphQL مفتوح للعامة | منع الاستعلامات الثقيلة وحماية الأداء والأمن |
| ADR-7 | تنفيذ منطق الطرف الثالث في **WASM/Isolate** بحدود صارمة | تشغيل كود عميل في نفس العملية | حماية الأداء والأمن ومنع «تطبيق واحد يبطّئ كل المتاجر» |
| ADR-8 | **ClickHouse** للتحليلات منفصلاً عن OLTP | تقارير مباشرة على Postgres | التقارير الثقيلة تقتل قاعدة المعاملات |
| ADR-9 | **قاموس حالات داخلي موحّد** للشحن والدفع | التعامل مع حالات كل مزود كما هي | يجعل التقارير والأتمتة ممكنة عبر كل الشركاء |

### 7.3 استراتيجية تعدد المستأجرين (Multi-tenancy)

- كل صف في كل جدول يحمل `tenant_id` غير قابل للتغيير؛ RLS مفعّلة على مستوى قاعدة البيانات (ليست شرطاً في كود التطبيق فقط).
- اختبار آلي في الـ CI: أي جدول جديد بلا سياسة RLS يُفشل البناء.
- حدود موارد لكل tenant (Rate limits، حجم استيراد، عدد أتمتات متزامنة) لمنع «الجار الصاخب».
- مفاتيح تشفير لكل tenant للبيانات الحسّاسة (هواتف/عناوين) مع دوران مفاتيح.

### 7.4 الموثوقية

| الجانب | الالتزام |
|---|---|
| Uptime النواة | 99.95% (Enterprise SLA)، 99.9% لبقية الباقات |
| RTO / RPO | ≤ 60 دقيقة / ≤ 5 دقائق |
| النسخ الاحتياطي | PITR يومي + اختبار استعادة شهري موثّق |
| النشر | Blue/Green + Canary + إمكانية Rollback خلال 5 دقائق |
| تدهور رشيق | إذا سقطت خدمة التوصيات أو التقييمات، يظل المتجر يبيع (Circuit breaker + fallback) |
| المراقبة | تتبع موزّع (OpenTelemetry) + SLOs مع Error budgets + تنبيهات على انتهاك الميزانية |

## 8. الأداء — «أهم حاجة» (Performance as a Contract)

> السرعة ليست هدفاً تحسينياً، بل **عقد** مفروض تقنياً على النواة والثيمات والتطبيقات.

### 8.1 أهداف تجربة المستخدم

| المقياس | الهدف (p75، موبايل، 4G مُقيّد) | الحد الأقصى المقبول |
|---|---|---|
| LCP — صفحة رئيسية/منتج | ≤ 1.2 s | 1.8 s |
| LCP — لاندنج بيدج | ≤ 1.0 s | 1.5 s |
| INP | ≤ 150 ms | 200 ms |
| CLS | ≤ 0.05 | 0.1 |
| TTFB (من الحافة) | ≤ 200 ms | 400 ms |
| زمن أول عرض بعد نقر «شراء الآن» | ≤ 500 ms | 900 ms |
| API لوحة التحكم p95 | ≤ 300 ms | 600 ms |
| بحث المنتجات p95 | ≤ 80 ms | 150 ms |
| إنشاء أوردر (end-to-end) p95 | ≤ 700 ms | 1.2 s |
| إنشاء شحنة لدى الناقل p95 | ≤ 2.5 s (غير متزامن مع تأكيد فوري للمستخدم) | — |

### 8.2 ميزانية الأداء (Performance Budget) — مفروضة في CI

| البند | الحد |
|---|---|
| JS حرج (Critical path) للواجهة | ≤ 100 KB gzipped |
| إجمالي JS للصفحة | ≤ 250 KB gzipped |
| CSS حرج | ≤ 25 KB |
| خطوط | ≤ ملفان، subset عربي/لاتيني، `swap` |
| صور فوق الطية | صورة واحدة LCP بأولوية `fetchpriority=high` |
| طلبات طرف ثالث قبل التفاعل | **صفر** |
| Lighthouse Performance (متجر مرجعي) | ≥ 95 |

**آلية الفرض:** فحص آلي على كل PR + على كل ثيم/تطبيق قبل النشر في المتجر. تجاوز الميزانية = فشل البناء، لا استثناءات بلا موافقة موثّقة.

### 8.3 التكتيكات التقنية

1. **تصيير على الحافة** مع ISR: صفحات المنتج والمجموعة مُخزّنة مسبقاً، وتُبطَل بدقّة عبر **Cache Tags** عند تغيّر السعر/المخزون فقط.
2. **جزيرة تفاعلية (Islands)**: HTML ثابت + ترطيب انتقائي للمكوّنات التفاعلية فقط (السلة، الفاريانتس).
3. **Streaming SSR**: بث الجزء العلوي من الصفحة فوراً وتأجيل الأقسام الثقيلة (التقييمات، التوصيات).
4. **Persisted GraphQL Queries**: لا استعلامات نصية على الشبكة؛ معرّف فقط ⇒ حجم أقل وأمان أعلى وقابلية Cache.
5. **Prefetch ذكي**: عند ظهور رابط منتج في الشاشة أو عند `mouseenter`/`touchstart`، يُجلب مسبقاً.
6. **صور تكيّفية**: AVIF/WebP، أحجام دقيقة، `srcset`، أبعاد ثابتة، Placeholder بلون سائد.
7. **تأجيل كل السكربتات غير الحرجة** (بيكسلات، شات، تحليلات) إلى ما بعد التفاعل أو عبر Web Worker.
8. **تحسين حسب الشبكة**: قراءة `navigator.connection` وتقليل جودة الصور تلقائياً على 2G/3G.
9. **قواعد بيانات**: فهارس مُصمّمة لأنماط الاستعلام، Connection pooling، قراءة من نسخ للقراءة، Cursor pagination بدل OFFSET.
10. **طوابير للعمليات البطيئة**: إنشاء الشحنة/إرسال الرسائل/مزامنة الكتالوج كلها غير متزامنة مع تحديث تفاؤلي في الواجهة.
11. **مراقبة مستخدم حقيقي (RUM)** لكل متجر مع تنبيه للتاجر: «ثيمك أبطأ 40% بعد تثبيت تطبيق X».
12. **اختبار حِمل دوري**: 10× ذروة الجمعة البيضاء كشرط إصدار.

### 8.4 أداء لوحة التحكم

- تحميل كسول للوحدات، جداول افتراضية (Virtualized) لعرض 50 ألف صف بسلاسة.
- عمليات جماعية غير متزامنة مع شريط تقدم ومتابعة في الخلفية.
- عمل جزئي بلا اتصال في تطبيق الموبايل مع مزامنة عند العودة.

## 9. طبقة التكاملات (Integration Fabric) — «الربط بين كل شيء»

### 9.1 المبدأ

بدل بناء تكامل مخصص لكل شريك، نبني **إطار موصّلات موحّد**: كل شريك يُنفّذ عقداً قياسياً، فيرث تلقائياً إعادة المحاولة، والمراقبة، والاختبارات، والتوثيق، ولوحة الحالة.

### 9.2 عقود الموصّلات (Connector Contracts)

| النوع | العمليات القياسية المطلوبة |
|---|---|
| **Shipping** | `getRates`، `createShipment`، `getLabel`، `track`، `cancel`، `schedulePickup`، `createReturn`، `getCODStatement` |
| **Payment** | `createIntent`، `capture`، `refund`، `void`، `getStatus`، `handleWebhook`، `tokenize` |
| **Messaging** | `sendTemplate`، `sendSession`، `getDeliveryStatus`، `handleInbound` |
| **Marketing/Ads** | `syncCatalog`، `sendEvent`، `getInsights` |
| **ERP/Accounting** | `syncProducts`، `syncOrders`، `syncInvoices`، `syncInventory`، `syncCustomers` |
| **Fulfillment/3PL** | `pushOrder`، `getStock`، `getFulfillmentStatus`، `pushReturn` |

كل موصّل يوفّر: ملف تعريف (اسم، دول مدعومة، حدود معدل، حقول إعداد)، بيئة اختبار (Sandbox)، ومجموعة اختبارات تعاقدية (Contract tests) تعمل يومياً على بيئة الشريك.

### 9.3 قواعد الموثوقية الإلزامية

| القاعدة | التفصيل |
|---|---|
| **Idempotency** | كل عملية كتابة خارجية تحمل مفتاحاً فريداً؛ التكرار لا يُنشئ شحنة/دفعة ثانية |
| **Outbox** | الحدث يُكتب في نفس معاملة قاعدة البيانات ثم يُنشر — لا فقدان ولا ازدواج منطقي |
| **إعادة المحاولة** | تراجع أسّي مع Jitter، حتى 24 ساعة، ثم DLQ مرئي للتاجر مع زر «أعد المحاولة» |
| **Circuit Breaker** | تعطيل مؤقت لموصّل متعثر مع تحويل تلقائي لبديل (خصوصاً الشحن والدفع) |
| **تطبيع الحالات** | تحويل حالات كل شريك إلى القاموس الداخلي؛ الحالات غير المعروفة تُعزل ولا تُتجاهل |
| **مراقبة صحة الشركاء** | لوحة عامة: زمن استجابة ونسبة نجاح كل شريك آخر 24 ساعة |
| **تسجيل مُنقّح** | لا نسجّل بيانات حسّاسة؛ مع إمكانية تتبع الطلب عبر `correlation_id` واحد من الواجهة حتى الشريك |

### 9.4 خارطة التكاملات المستهدفة

| الفئة | الشركاء (مرحلة 1) | (مرحلة 2+) |
|---|---|---|
| الشحن — مصر | بوسطة، مايلرز، شيب بلو، أرامكس، J&T، QP Express | فيدكس، DHL، مناديب ذاتيون |
| الشحن — الخليج | SMSA، Naqel، Torod، أرامكس | Barq، iMile، Fetchr |
| المدفوعات | Paymob، Fawry، Kashier، PayTabs، MyFatoorah | Tap، HyperPay، Stripe، PayPal |
| BNPL/تقسيط | تابي، تمارا، valU | سِمبل، أميت، تقسيط بنكي |
| المراسلة | WhatsApp Business API، SMS محلي، بريد | ماسنجر، إنستجرام، تيليجرام |
| الإعلانات | Meta CAPI، TikTok Events، Google Ads، Snapchat | Twitter/X، Pinterest |
| قنوات البيع | Instagram/Facebook Shops، TikTok Shop، Google Shopping | أمازون، نون، جوميا |

### 9.5 وحدة «الربط لأي شيء» (Universal Connector)

لكل ما لا يوجد له موصّل جاهز:
- **Webhooks صادرة** بتوقيع HMAC وفلترة أحداث وقوالب حمولة مخصصة.
- **HTTP Action داخل محرك الأتمتة**: استدعِ أي API خارجي كخطوة في الأتمتة، مع تعيين الحقول (Field mapping) بواجهة مرئية.
- **مستورد/مصدّر ملفات مجدول** (SFTP/S3/Google Drive) للأنظمة القديمة.
- **موصّل مخصص بلا كود**: عرّف Base URL + المصادقة + تعيين الحقول، واحصل على موصّل يعمل — مع إمكانية نشره في متجر التطبيقات.

### 10.4 قواعد ذهبية للتسعير

1. **لا حبس للبيانات**: التصدير الكامل متاح في كل الباقات — نكسب بالقيمة.
2. **لا عقوبة على النجاح**: العمولة لكل أوردر تسقط تماماً من Pro فما فوق، فلا يُعاقَب النمو.
3. **الترقية بلا هجرة**: نفس المتجر ونفس الروابط ونفس البيانات — تبديل باقة فوري.
4. **حاسبة شفافة**: أداة تُظهر للتاجر أيّ نموذج أرخص له بناءً على أوردراته الفعلية، وتقترح التبديل تلقائياً إذا وفّر له مالاً (ثقة > إيراد قصير الأجل).
5. **تسعير محلي بالعملة المحلية** لكل سوق، مع باقات معايرة على القدرة الشرائية لا مجرد تحويل عملة.
6. **لا رسوم خفية** — كل رسم يظهر في فاتورة مفصّلة.

### 10.6 وحدة اقتصاد الوحدة (Unit Economics) — إطار للتحقق

- **CAC** المستهدف عبر PLG ≤ ثلث القيمة الدائمة السنوية.
- **الهامش الإجمالي المستهدف**: ≥ 72% (بعد استضافة الحافة، وتكلفة الرسائل، وتكلفة الدفع).
- **نقطة التعادل للتاجر المجاني**: يجب أن يغطّي دخل العمولة + هامش الشحن تكلفة استضافته خلال ≤ 60 يوماً من التفعيل، وإلا نضبط حدود الباقة المجانية.

| سجل التدقيق | كل إجراء حسّاس (تغيير سعر، تصدير عملاء، تغيير بنك التحويل) مسجَّل وغير قابل للتعديل |

| توطين البيانات | خيار تخزين بيانات السوق داخل نطاقه الجغرافي (مطلب سعودي/إماراتي متكرر) |
| مكافحة الاحتيال | حماية من هجمات حشو بيانات الاعتماد، حدود معدل، CAPTCHA تكيفي، كشف بوتات على الشيك أوت |

| المحتوى | سياسة استخدام مقبول تمنع بيع السلع المحظورة والمنتجات المقلّدة، مع أدوات إبلاغ ومراجعة |
| الشفافية للمستهلك | سياسة استرجاع واضحة إلزامية، وبيانات التاجر ظاهرة، وآلية شكوى |

### ملحق هـ — تعريف «تم» (Definition of Done)

ميزة لا تُعتبر مكتملة إلا إذا:
1. مغطّاة باختبارات (وحدة + تكامل + E2E للمسارات الحرجة).
2. لا تكسر ميزانية الأداء (تقرير آلي مرفق بالـ PR).
3. موثّقة للتاجر (مقال مساعدة) وللمطوّر (مرجع API) بالعربية والإنجليزية.
4. لها أحداث تتبع (Analytics events) ومقياس نجاح مُعلن.
5. مراجعة أمنية للحقول الحسّاسة والصلاحيات.
6. تعمل خلف علم ميزة مع خطة تراجع (Rollback).
7. مترجمة بالكامل وتعمل في RTL.
8. لها سلوك واضح عند فشل التبعية الخارجية (لا شاشة بيضاء).
